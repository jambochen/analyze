## 我在用什麼標準判斷

先說標準，不然下面的理由會顯得很武斷。我主要問四件事：

1. 誰會用這個結果？
2. 他們手上是不是已經有更好的資料？
3. **我有什麼是他們拿不到的？**
4. **這份資料的不同時期，裝的是同一群東西嗎？**

第三個最關鍵。如果資料的主人自己就能做這個分析、而且做得比我們好，
那報告就沒有存在的理由。房價是最典型的例子——仲介跟銀行手上的資訊
遠比公開實價登錄多，我們算不出他們不知道的事。

第四個是我這次查資料才加進來的，原因寫在下面。

另外課程要求報告最後要有**預測**或**具體建議**，兩個有一個就好，
但兩個都沒有的話再漂亮也不行。

## 四個資料集

### EV 電池健康

**這份是合成的，而且合成規則可以直接反推出來。**

我跑出來發現欄位之間有恆等式：

```
capacity_loss_percent + battery_health_percent   平均=100.0  標準差=0.0000000000
corr(state_of_health, battery_health_percent)    =  0.9898
corr(thermal_health_score, thermal_runaway_risk) = -0.9868
```

標準差是 0，意思是這兩欄**永遠加起來等於 100**，根本是同一個數字的
兩種寫法，不是什麼「高度相關」。

缺失率也很可疑：70 欄裡有 67 欄的缺失率都落在 3.05%–4.94% 這個很窄的
範圍，剩下 3 欄剛好是 0%。真實的感測器不會這樣壞——這比較像是先造好
完整資料、再按固定比例隨機挖洞。

所以裡面好幾個「預測目標」其實是別的欄位算出來的。在這上面建模，
跑出來的是合成程式的參數，不是電池的行為。頁面也沒說資料哪來的。

### 學生考試表現

這份沒什麼好講的，8 欄裡 5 個類別、3 個分數，沒有時間、沒有空間、
沒有階層。而且不知道在講誰——沒說學校、年份、國家，`race/ethnicity`
直接編成 group A 到 E，連是什麼意思都沒有對照表。母體沒定義，
那推論就沒有對象。

另外它下載了 51 萬次，大概是 Kaggle 上被做爛得最徹底的資料集之一。

### 臺北市實價登錄

房價這個方向我先前評估過，卡在第二個問題就過不去（仲介銀行資訊比我們多）。
不過就算撇開這點，**這份也是加工過的二手版本，比內政部原始檔差**。

時間跨度名義上 1986–2020，實際上：

```
2019 年佔 93.3%，加上 2020 年共 98.3%
剩下 8 個年度合計 103 筆
```

還有兩個欄位的名字跟內容對不上：

```
building_age （叫屋齡）  範圍 1907–2020  ← 其實是西元年
complete_year（叫建成年）範圍 0–108      ← 其實是民國年
```

行政區英譯也亂掉了（`Beitou`、`shihlin` 沒有 District，`Zhongshan Area`
用 Area），`urban_land_use` 出現 `Quotient`、`work` 這種機翻殘留，
`main_use` 裡 `Other` 跟 `Others` 並存。原始中文編碼已經沒了。

如果之後真的要做房價，建議直接去拿內政部原始檔。

### AI 對就業薪資

**這份最可惜，我花最多時間在它身上。** 它表面品質是四份裡最好的，
幾乎沒有 null，還附了 data dictionary。問題不在資料髒。

**最大的問題：AI 曝險分數根本不在檔案裡。**

標題叫 "AI Impact"，描述引用了 ILO 的生成式 AI 職業曝險指數。
但實際 17 個欄位裡，**沒有任何一欄是曝險度**。

這裡要幫上傳者說句話：附的 data dictionary 本身沒有騙人，它寫
`isco_group_hint` 是 "for joining **against** AI-exposure data"，
明講這是拿來**對外接合**的鍵，ILO 那份是**待接合的外部來源**。
誤導是來自 Kaggle 的標題跟描述，不是字典。

但結果一樣——這份資料拆掉包裝就是 ai-jobs.net 的薪資表加兩個分類欄。
要做 AI 曝險的題目得自己去 ILO 接，那這份的價值就很有限了。

**再來是沒辦法識別因果。** 沒有個人 ID（同一個人跨年追蹤不了）、
沒有公司 ID、也沒有對照組（全部都是 AI／資料類職缺）。
能算的頂多是「不同職種在不同年度的薪資差異」，那是橫斷面關聯，
不是「AI 的影響」。

**還有年度分布很畸形：**

```
work_year   筆數     remote_ratio 均值
2020          75          62.0
2021         214          69.6
2022       1,114          58.5
2023       4,538          36.8
2024      27,690          22.5
2025      38,282          23.3
```

2024+2025 佔了 91.8%，而標題寫的 2026 年**一筆都沒有**。

那個 `remote_ratio` 的曲線看起來完美呈現「疫情遠端高峰然後回落」，
但 2020–2021 加起來才 289 筆，而且早期會去填 ai-jobs.net 的人
本來就偏遠端優先的新創。樣本組成的變化跟真實趨勢完全混在一起。

## 順便講一下我為什麼特別查這份

因為這份底下有人做了一份**方法很用心**的分析，
sasakitetsuya 的 *AI Salaries and the Vanishing Middle*，
是該資料集票數最高的 notebook。

那份有事前假說、自建可調整的職稱分類、OLS 控制四個混淆變數、
交互項、兩組敏感度分析，最後還誠實地否定了自己原本假說的兩條腿。
以 Kaggle 的標準來說做得相當好。

他也獨立證實了我上面講的——他在 notebook 裡直接寫
"the exposure columns are **not present**"。

**但他的主結論撐不住。** 他的核心發現是「管理職 2023→2025 薪資 +22%」，
我復現他的樣本之後：

```
Management      2023  n=   140   ← 基期就 140 筆
People-facing   2023  n=    11
Middle          2023  n= 3,756
```

他在 caveat 裡有承認 People-facing 只有 11 筆，**但沒提 Management
也才 140 筆**，而 +22% 就是從這個基期算出來的。

更關鍵的是那一組裝的人換掉了：

```
2023 (n=140)  ：Data Manager 58、Head of Data 21、Data Analytics Manager 19
2025 (n=4,400)：Manager 2,238、Director 472、Data Manager 326
```

2023 年那組是「資料部門的主管」，2025 年主體變成泛用的
`Manager`／`Director`，組內 Executive 比例也從 24.3% 掉到 13.3%。

**這不是同一群人薪水在漲，是這組裝的人換了。** 他迴歸有控制年資，
但控不住職稱本身的意思在漂移。

所以我才把「時間可比性」加成第四個判斷標準。一份做得這麼用心的分析
還是撞上這面牆，代表這不是技巧能補救的，得在選題階段就先問。

## 我目前推薦的

**候選 I：美國航班延誤的低報稽核。** 目前唯一四個問題都答得出來的。

研究問題是：以實際觀測氣象為基準，哪些航空公司跟機場系統性地少報
天氣延誤？能不能量化排序，給監理單位當查核優先順序。

| | |
|---|---|
| 誰會用 | DOT / FAA 監理單位 |
| 他們有更好的嗎 | 沒有。OIG 已經認定 BTS 的延誤成因欄位不可信，但沒給替代方法 |
| 我有什麼他們沒有 | **機場對 NOAA 氣象測站的對照表**，發布者說這「不存在於任何維護中的公開資料」 |

**這題的結構優勢是：掌握資料的航空公司沒有動機自己做這個分析。**

資料 4,280 萬筆航班（2019-01 至 2025-07），有 24 個月的入門檔
1,406 萬列約 1.1 GB，schema 一樣，可以先用小的。

它的欄位前綴設計我覺得是亮點，實測確認：

```
wx        106 欄   航班資訊截止點「之前」的氣象，可以安全用
oracle     54 欄   航班自己事件時刻的氣象，拿來預測就是洩漏
reported    5 欄   航空公司自報的延誤成因，刻意留著但標明不可信
其他        46 欄   航班識別、日曆、壅塞度、前段航班
```

**等於把洩漏風險寫進欄位命名裡**，這對我們是實質的保護。

關鍵賣點我也跑了（入門檔，僅供篩選非分析結果）：

```
起點天氣    班次          平均抵達延誤   取消率
VFR      11,910,145        6.02 分      1.12%
MVFR      1,293,044        8.52 分      1.78%
IFR         492,421       15.76 分      3.26%
LIFR        344,515       17.83 分      3.52%
```

VFR 到 LIFR 是天氣從好到壞，延誤跟取消率**單調上升**，
所以「實際氣象 vs 自我回報」的落差是算得出來的。

代價是完整版 6.1 GB，而且要嚴守紀律——`oracle_` 開頭的欄位絕對
不能進預測模型。

**台灣做不了這題**，不是資料難拿，是台灣根本**沒有「航空公司自報
延誤成因」這個欄位**。民航局只有月彙總，TDX 只有班表跟即時資訊。
少了自報這個對照基準，「低報稽核」這個題目就不存在。

### 其他還在檯面上的

**候選 J（2020 逐張選票）**：實測結果是所有候選裡最乾淨的，
1.66 億列跟論文宣稱差異 0，方法論上限也最高（可以正面處理生態謬誤）。
但第三個問題答不出來——這就是選舉研究社群自己發的資料，CC0 誰都能下載，
他們自己已經發過 Nature 子刊了。

**候選 C（BRFSS 健康行為）**：唯一能正當做複雜抽樣加權估計的資料，
七個設計變數都完整、1,306 個分層沒有單一觀測層。但同樣沒有資訊優勢，
而且資料停在 2015。

這份有個坑我覺得值得提，滿容易中的：

```
_HCVU651 的值分布
  1.0  →  252,542
  9.0  →  159,253    ← 碼 9 = 不知道／拒答
  2.0  →   29,661

null_count = 0
```

**BRFSS 把「不知道／拒答」編成碼 9，是有效整數不是 null。**
`null_count` 回報 0%，看起來完全沒缺失，實際上這欄 36% 是無效回答。
直接拿去算平均會得到一個看起來很合理的錯數字。

**候選 N（台灣交通事故）**：台灣候選裡受益者最明確的，
道安會跟地方交通局，建議也具體。還沒實測。

**候選 H（PJM 電網）**：這個我這次把它往上調了。原本我把它排很後面，
理由是「負載預測的使用者是調度單位」，但**我後來覺得當初問錯了問題**
——負載預測不是這份資料唯一能做的，而且是最不該做的那個。

它真正撐得起的是「氣象效應 vs 資料中心結構性成長」的分離，
而 PJM 作為市場營運者，對這件事做公開歸因會牽動成本分攤爭議，
**沒有動機自己做**。受益者是 FERC 跟州監理單位，不是調度單位。
這個結構跟候選 I 其實是同一類。

## 幾個我踩過的坑，給大家參考

- **`null_count` 是 0 不代表沒缺失**（BRFSS 碼 9）
- **不要假設叫 id 的欄位是全域唯一**（候選 J 的 `cvr_id` 只在郡內唯一，
  單欄去重低估 5.5 倍）
- **聚合前先檢查字串有沒有多種拼法**（`JOSEPH R BIDEN` 跟
  `JOSEPH R. BIDEN` 差一個句點，直接 group_by 低估 17%）
- **欄位名稱不等於欄位語意**（實價登錄的屋齡存西元年；
  台電的「中送北潮流」82% 時間是負的，名字講的是量測慣例不是實際流向）
- **欄位相加恆為常數、相關係數接近 ±1 = 合成資料的指紋**
- **跨年比較前先分年看各組樣本數跟組內構成**，不要只看總列數
- **polars 的瓶頸是分組數不是列數**（1.66 億列全掃只要 0.1 GB，
  但 4,620 萬組的 group_by 會撐爆 16 GB）
