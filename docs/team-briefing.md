## EV 電池健康

合成資料，而且合成規則可以反推。

```
capacity_loss_percent + battery_health_percent   平均=100.0  標準差=0.0000000000
corr(state_of_health, battery_health_percent)    =  0.9898
corr(thermal_health_score, thermal_runaway_risk) = -0.9868
```

標準差 0，代表這兩欄恆等於 100，是同一個數字的兩種寫法。

缺失率也不對：70 欄裡 67 欄落在 3.05%–4.94% 的窄帶，剩下 3 欄剛好 0%。
真實感測器不會這樣缺，這是先造完整資料再按固定比例挖洞的特徵。

結果是好幾個「預測目標」其實是別的欄位算出來的。在這上面建模跑出來的
是合成程式的參數，不是電池行為。頁面也沒說資料來源。

## 臺北市實價登錄

加工過的二手版本，比內政部原始檔差。

時間跨度名義上 1986–2020，實際上 2019 年佔 93.3%，加上 2020 年共 98.3%，
剩下 8 個年度合計 103 筆。

兩個欄位名稱與內容對不上：

```
building_age （叫屋齡）  範圍 1907–2020  ← 實際是西元年
complete_year（叫建成年）範圍 0–108      ← 實際是民國年
```

行政區英譯不一致（`Beitou`、`shihlin` 無 District，`Zhongshan Area` 用 Area），
`urban_land_use` 有 `Quotient`、`work` 這類機翻殘留，`main_use` 裡
`Other` 與 `Others` 並存。原始中文編碼已遺失。

要做房價建議直接取內政部原始檔。

另外房價這個方向本身也有問題：仲介與銀行手上的資訊遠多於公開實價登錄，

## AI 對就業薪資

表面品質最好的一份，幾乎沒有 null，附了 data dictionary。問題不在資料髒。

**AI 曝險分數不在檔案裡。** 標題叫 "AI Impact"，描述引用 ILO 的生成式 AI
職業曝險指數，但 17 個欄位沒有任何一欄是曝險度。

附的 data dictionary 本身沒有誤導——它寫 `isco_group_hint` 是
"for joining **against** AI-exposure data"，明指這是對外接合的鍵，
ILO 那份是待接合的外部來源。誤導來自 Kaggle 的標題與描述。

但結果一樣：拆掉包裝就是 ai-jobs.net 的薪資表加兩個分類欄。

**無法識別因果。** 沒有個人 ID、沒有公司 ID、沒有對照組（全是 AI／資料類
職缺）。能算的頂多是不同職種在不同年度的薪資差異，屬橫斷面關聯。

**年度分布畸形：**

```
work_year   筆數     remote_ratio 均值
2020          75          62.0
2021         214          69.6
2022       1,114          58.5
2023       4,538          36.8
2024      27,690          22.5
2025      38,282          23.3
```

2024+2025 佔 91.8%，標題寫的 2026 年沒有資料。

`remote_ratio` 那條曲線看似呈現「疫情遠端高峰後回落」，但 2020–2021
合計 289 筆，且早期填報者偏遠端優先的新創。樣本組成變化與真實趨勢
混在一起。

### 復現了這份底下票數最高的 notebook

sasakitetsuya 的 *AI Salaries and the Vanishing Middle*。方法設計用心：

最後否定了自己原假說的兩條腿。

他也獨立證實了曝險欄位的問題，notebook 裡直接寫
"the exposure columns are **not present**"。

但主結論撐不住。核心發現是「管理職 2023→2025 薪資 +22%」，復現其樣本：

```
Management      2023  n=   140
People-facing   2023  n=    11
Middle          2023  n= 3,756
```

caveat 裡承認了 People-facing 的 11 筆，沒提 Management 也才 140 筆，
而 +22% 正是從這個基期算的。

更關鍵的是那組裝的人換了：

```
2023 (n=140)  ：Data Manager 58、Head of Data 21、Data Analytics Manager 19
2025 (n=4,400)：Manager 2,238、Director 472、Data Manager 326
```

2023 年是資料部門主管，2025 年主體變成泛用 `Manager`／`Director`，
組內 Executive 比例從 24.3% 降到 13.3%。不是同一群人薪水在漲，
是這組裝的人換了。迴歸控制了年資，控不住職稱本身的語意漂移。

## 我目前推薦的

**候選 I：美國航班延誤的低報稽核。**

研究問題：以實際觀測氣象為基準，哪些航空公司與機場系統性少報天氣延誤？
能否量化排序，作為監理查核的優先順序。

DOT／FAA 是使用者，而 OIG 已認定 BTS 的延誤成因欄位不可信但沒給替代方法。
這份資料的機場對 NOAA 測站對照表，發布者說「不存在於任何維護中的公開資料」。
**掌握資料的航空公司沒有動機自己做這個分析**，這是這題的結構優勢。

4,280 萬筆航班（2019-01 至 2025-07），有 24 個月入門檔 1,406 萬列約 1.1 GB，
schema 相同。

欄位前綴設計是亮點：

```
wx        106 欄   航班資訊截止點「之前」的氣象，可安全使用
oracle     54 欄   航班自身事件時刻的氣象，用於預測即洩漏
reported    5 欄   航空公司自報的延誤成因，刻意保留但標明不可信
其他        46 欄   航班識別、日曆、壅塞度、前段航班
```

等於把洩漏風險寫進欄位命名。

關鍵賣點實測（入門檔，僅供篩選非分析結果）：

```
起點天氣    班次          平均抵達延誤   取消率
VFR      11,910,145        6.02 分      1.12%
MVFR      1,293,044        8.52 分      1.78%
IFR         492,421       15.76 分      3.26%
LIFR        344,515       17.83 分      3.52%
```

天氣從好到壞，延誤與取消率單調上升，「實際氣象 vs 自我回報」的落差
算得出來。

代價：完整版 6.1 GB，且 `oracle_` 欄位絕對不能進預測模型。

台灣做不了這題——不是資料難拿，是台灣沒有「航空公司自報延誤成因」
這個欄位。少了這個對照基準，低報稽核這個題目不存在。

## 幾個踩過的坑

- `null_count` 是 0 不代表沒缺失。BRFSS 把「不知道／拒答」編成碼 9，
  是有效整數，`_HCVU651` 這欄 36% 是無效回答但 `null_count` 回報 0
- 不要假設叫 id 的欄位全域唯一。候選 J 的 `cvr_id` 只在郡內唯一，
  單欄去重低估 5.5 倍
- 聚合前檢查字串拼法。`JOSEPH R BIDEN` 與 `JOSEPH R. BIDEN` 差一個句點，
  直接 group_by 低估 17%
- 欄位名稱不等於語意。實價登錄的屋齡存西元年；台電的「中送北潮流」
  82% 時間為負，名稱講的是量測慣例不是實際流向
- 欄位相加恆為常數、相關係數接近 ±1，是合成資料的指紋
- 跨年比較前先分年看各組樣本數與組內構成，不要只看總列數
- polars 的瓶頸是分組數不是列數。1.66 億列全掃 0.1 GB，
  但 4,620 萬組的 group_by 撐爆 16 GB
